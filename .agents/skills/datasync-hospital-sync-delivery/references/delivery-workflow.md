# 医院数据回传交付流程

## 1. 分类和证据

先把任务归入一个或多个阶段：协议契约、CYYY 拉取、LHYY 校验、结构适配、导入/附件、ACK、恢复/补写、维护互斥、用户可见验收。

按以下顺序收集证据：

1. 当前失败现象、状态记录和脱敏日志。
2. Common 协议和状态定义。
3. CYYY/LHYY 当前实现及对应测试。
4. 部署配置键、挂载契约和项目文档。
5. 必要时的只读数据库或容器状态；不得在未授权时执行写操作。

至少比较：输入不合法、身份/包链不一致、暂时性传输失败、持久危险状态、导入已成功但审计未完成、附件物理存储不一致等候选原因。

## 2. 变更边界

- Common 协议变更必须同步检查 CYYY 生产者、LHYY 消费者和兼容测试。
- CYYY 拉取变更要保持严格 SSH、流式 hash、原子发布、失败重试和稳定 ackId。
- LHYY 校验变更要在备份前拒绝不可信输入，并维持 manifest、checksum、医院范围和包链一致。
- 结构适配只能扩大明确批准的兼容范围；校验列集合和实际写入列集合必须相同。
- 导入/恢复变更必须维护数据库事务、附件切换、持久状态栅栏、维护锁和 reconciliation 证明。
- 用户可见附件必须从 NTCare 实际页面验证；直接查数据库或文件存在不能替代端到端验收。

## 3. 验证阶梯

1. 新增或运行最小聚焦测试，覆盖主路径和触发本次问题的失败路径。
2. 运行受影响测试项目。
3. 运行 `.\.codex\tools\verify.ps1 -Level Project`。
4. 协议、恢复、安全或交付变更运行 `-Level Full`。
5. 可用环境中进行真实业务顺序的人工验证；没有环境时明确列为未验证，不用模拟成功替代。

必须检查重复执行、进程中断、旧状态、部分成功、审计补写失败、路径逃逸、包身份错配和并发维护冲突中与本次变更相关的场景。

## 4. 知识和证据

- 业务或流程稳定行为改变时，更新 `datasync-business-logic/references/followup-hospital-sync.md` 和知识映射。
- 每轮报告、截图和原始日志进入忽略目录；仓库只保留稳定契约、长期安全决策和实施 runbook。
- 完成摘要包含：根因/方案、变更范围、验证命令与结果、未验证项、回滚入口、知识影响。
